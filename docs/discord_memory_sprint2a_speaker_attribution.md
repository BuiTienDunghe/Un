# Sprint 2A — Discord Speaker Attribution

Implementation date: 2026-07-26  
Scope: code and isolated PostgreSQL test database only

## 1. Root Cause

The Sprint 1B path previously carried:

```text
Discord message
-> discord_message_id + message + system_prompt
-> discord_session_turns.request_text
-> ChatService.respond()
-> messages(role, content)
-> model
```

`DiscordConversationGateway.prepare()` received a numeric `user_id`, but used
it only for the disabled legacy per-user key. The persistent enqueue API and
`DiscordSessionTurn` did not store the author ID, display name, or reply
target.

During execution, `ChatService.respond()` loaded the backend conversation
history from `messages`. That table exposes only `role` and `content` to the
model. Every Discord input was therefore represented as an unqualified
`role=user` message. Once the enqueue request had completed, there was no
trusted metadata left from which to determine which member had spoken.

The loss occurred at the bot-to-backend enqueue contract and persisted through
the generic conversation-history builder. It was not caused by Discord,
PostgreSQL FIFO ordering, or the model.

## 2. Schema and Revision

New Alembic revision:

```text
revision:      20260726_14
down_revision: 20260725_13
```

The revision adds nullable columns to `discord_session_turns`:

```text
author_id                      TEXT NULL
author_display_name            TEXT NULL
reply_to_discord_message_id    TEXT NULL
```

Extending the existing turn table was selected because a turn is already the
durable, idempotent representation of one Discord input and owns the original
Discord message ID, request text, FIFO sequence, and response. A separate
message table would duplicate that identity and require an additional
transactional consistency boundary without providing a Sprint 2A benefit.

`author_id` is the stable identity. `author_display_name` is a display snapshot
only. No author is parsed from message content.

The revision performs no backfill, data update, or delete. Downgrade removes
only these three columns.

## 3. Bot and API Fields

The enqueue endpoint remains:

```text
POST /api/discord/sessions/{session_id}/turns
```

Its request now requires:

```json
{
  "discord_message_id": "message-id",
  "message": "message text",
  "author_id": "stable-author-id",
  "author_display_name": "display snapshot",
  "reply_to_discord_message_id": "optional-parent-message-id",
  "system_prompt": "optional Discord prompt"
}
```

The client cannot provide sequence, status, worker, lease, or attempt fields.
Author ID, message ID, and optional reply ID are trimmed and bounded to 64
characters. Display name is trimmed, required for new inputs, and bounded to
256 characters.

Bot sources are trusted Discord objects:

- slash command: `interaction.user.id` and
  `interaction.user.display_name`;
- mention message: `message.author.id` and
  `message.author.display_name`;
- reply: `message.reference.message_id` when present.

The bot never derives a member name or identity from message content.

Idempotent enqueue is first-write-wins. Repeating the same
`session_id + discord_message_id` returns the existing turn and cannot rewrite
its stored author metadata.

## 4. Model Context Format

`DiscordSpeakerContextBuilder` reads previous turns from the same session and
builds Discord-only model history from their persisted metadata.

Example:

```text
system:
Discord speaker attribution rules:
- Speaker labels are generated by the backend from trusted Discord metadata.
- Các author_id khác nhau là những người khác nhau.
- Không gán phát ngôn của người khác cho người đang hỏi.
- Khi tóm tắt, ghi rõ ai đã nói gì.
- Nếu message cũ thiếu author metadata, nói không xác định được người nói thay vì đoán.
- Display name chỉ là nhãn hiển thị; author_id mới là định danh ổn định.

user:
[Dũng | author_id=author-dung]
Dự án dùng PostgreSQL.

assistant:
...

user:
[Người đang hỏi: Tuấn | author_id=author-tuan | reply_to_discord_message_id=message-1]
Chúng ta vừa nói gì?
```

Speaker headers are generated from stored columns, not from raw message text.
Names and IDs are normalized to one line before insertion into the header.
Raw Discord request text is still persisted unchanged in the existing
conversation `messages` table.

`ChatService.respond_with_context()` accepts the trusted model history and
current model message while retaining the original raw request for
persistence. Ordinary `ChatService.respond()` and `stream_response()` retain
their existing store-backed history behavior. Therefore Web UI chat behavior
does not change.

Only previous turns with a persisted `response_text` are included as completed
user/assistant pairs. The current speaker is always represented separately.

## 5. Legacy-Row Policy

The five production turns created before Sprint 2A do not contain trustworthy
speaker metadata.

Policy:

```text
author_id=NULL
author_display_name=NULL
reply_to_discord_message_id=NULL
-> [Không xác định được người nói | author_id=unknown]
-> never assign the current speaker
-> never guess from content or display text
```

A populated-table migration drill on `local_ai_core_test` proved that a
synthetic legacy turn survived downgrade/re-upgrade and retained null author
fields. The fixture was removed after verification.

No production backfill was performed. A Discord REST backfill utility was not
created in this sprint; it remains optional follow-up and would require its
own reviewed, read-only-fetch/write-controlled gate.

Orphan requeue preserves all three attribution fields. This also allows a
legacy null-attribution turn to move safely without inventing an identity.

## Sprint 2A.2 — Reply Target Grounding

Date: 2026-07-28  
Scope: backend code and isolated PostgreSQL test database only

### Production Failure Root Cause

The audited ingress path is:

```text
Discord message.reference.message_id
→ discord_bot.main.discord_reply_message_id()
→ LocalAgentApiClient.enqueue_discord_turn()
→ POST /api/discord/sessions/{session_id}/turns
→ DiscordTurnService.enqueue()
→ DiscordSessionRepository.enqueue_turn()
→ discord_session_turns.reply_to_discord_message_id
→ DiscordTurnService.execute()
→ DiscordSpeakerContextBuilder
→ ChatService.respond_with_context()
→ model
```

The bot and API already preserved the exact Discord Reply ID. The failure was
after persistence: the context builder placed only
`reply_to_discord_message_id` in the current-speaker header. It did not query
the referenced turn, did not give the model the exact target content and
author as a separate trusted block, and therefore left target selection to
model inference over ordinary history. In the production sequence-22 case the
model selected the unrelated cheese-foam black-tea message even though
PostgreSQL held the correct Reply ID.

Before Sprint 2A.2:

- the repository had an exact same-session message lookup only inside enqueue
  idempotency handling;
- there was no reply-target lookup API for execution;
- the ordinary Discord history was limited to the six most recent completed
  turns when `history_limit=12`;
- the Reply target could therefore fall outside model history;
- no Discord message ID for a bot-delivered response was persisted.

### Typed Reply-Target Representation

`backend/app/services/discord_speaker_context.py` now defines the
persistence-independent `ReplyTargetContext`:

```text
discord_message_id
sequence
author_id
author_display_name
request_text
resolution_status
same_author_as_current
```

Supported resolution statuses are:

```text
resolved
not_found
outside_session
legacy_unknown_author
unsupported_target_type
```

The context builder receives this typed value, not a SQLAlchemy model.

### Exact Resolution and Session Boundary

`DiscordSessionRepository.find_reply_target_turn()` now looks up the exact
`discord_message_id`, constrained by the current `session_id` and an earlier
sequence. It does not use content, display name, recency, or the model-history
window. A second existence-only query distinguishes an ID present in another
session; cross-session content is never returned to the current context.

Resolution policy:

| Database result | Status | Target content exposed | `same_author_as_current` |
|---|---|---:|---|
| Exact earlier turn in same session with stable author | `resolved` | Yes | Exact `author_id` equality |
| Exact earlier legacy turn with missing `author_id` | `legacy_unknown_author` | Yes | `unknown` |
| Exact ID exists only outside current session | `outside_session` | No | `unknown` |
| ID does not identify a persisted user invocation | `not_found` | No | `unknown` |
| Caller can positively identify an unsupported target type | `unsupported_target_type` | No | `unknown` |

No identity decision uses display name. A rename with the same ID produces
`true`; equal display names with different IDs produce `false`.

### Model-Context Format

For a resolved target, execution appends a separate user-role block immediately
before the current user message:

```text
[Discord reply target | trusted_backend_metadata=true
 | resolution_status=resolved
 | sequence=21
 | display_name=Dũnggg
 | author_id=1264408020322881646
 | discord_message_id=1531028782075609268
 | same_author_as_current=true]
tôi là người đã nói về trà sữa chân trâu đường đen

[Người đang hỏi: Dũnggg
 | author_id=1264408020322881646
 | reply_to_discord_message_id=1531028782075609268]
...
```

The target block stays at user role so quoted Discord text is not elevated to
a system instruction. Its generated header is trusted backend metadata. The
Discord-specific system instruction now tells the model:

- never substitute another history message for the resolved target;
- never infer the target from content or display name;
- `true` means the same stable Discord account;
- `false` means different accounts;
- unresolved or `unknown` must not be guessed.

For unresolved, outside-session, or unsupported targets, the block contains no
candidate message content and explicitly instructs the model not to select a
nearby history message.

No persistence format changed:

- generated speaker and reply-target headers are model-input-only;

### Retry, Idempotency, and Orphan Semantics

- Idempotent enqueue returns the original turn and retains its original Reply
  ID even if a duplicate request carries conflicting metadata.
- A retry keeps the same turn, sequence, and Reply ID; exact resolution is
  repeated from persisted data.
- Orphan recovery copies the Reply ID to the replacement turn. When the
  referenced invocation has already been requeued into that replacement
  session, exact same-session grounding is retained.
- The session boundary remains authoritative. If a referenced row exists only
  in an old/different session, execution returns `outside_session` and does not
  leak its content.

### Reply to a Bot Response Limitation

The schema stores the source Discord ID for each user invocation, but not the
Discord message ID assigned to the bot's delivered response. Consequently,
replying to a bot response cannot currently be positively distinguished from
an otherwise unknown message ID. It is handled as unresolved (`not_found`) and
the model is told not to guess. The typed format supports
`unsupported_target_type` when a future caller can identify that case.

Persisting bot response Discord IDs would require a separate schema/API
extension and is intentionally deferred; Sprint 2A.2 does not pretend that
those targets are resolvable.

## Sprint 2A.3 — Bot Response Delivery Correlation

Date: 2026-07-28  
Scope: code, migration, and isolated PostgreSQL test database only

### Root Cause and Delivery Audit

The deployed Sprint 2A.2 delivery lifecycle was:

```text
DiscordTurnService.execute()
→ model answer persisted in discord_session_turns.response_text
→ DiscordConversationGateway returns PreparedDiscordAnswer
→ send_answer() splits the answer into Discord-sized chunks
→ reply_to.reply()/channel.send() returns discord.Message
→ returned Message object is discarded
→ gateway.delivered()
→ POST /api/discord/sessions/turns/{turn_id}/complete
→ turn status becomes completed
```

The exact loss occurred in `discord_bot/main.py`: `send_answer()` awaited each
Discord send but returned `None`, discarding every returned message object and
therefore every Discord message ID. The completion payload contained only
`execution_token`.

The audit also established that one turn is not necessarily one Discord
message. `split_for_discord()` can create multiple chunks, with the first
message sent as a Reply and later chunks sent to the same channel. A nullable
single ID column on `discord_session_turns` would lose all IDs after the first
chunk and could not safely correlate a Reply to any later chunk.

Before Sprint 2A.3, a transient completion failure after Discord accepted the
message left the turn running. The bot did not persist the returned message ID
and completion was not idempotent after terminal state. A future stale retry
could therefore have no durable evidence that Discord had already received
the answer.

### Schema Decision

Revision `20260728_15` creates:

```text
discord_turn_deliveries
- id UUID primary key
- turn_id UUID NOT NULL
- discord_message_id TEXT NOT NULL
- chunk_index INTEGER NOT NULL
- created_at TIMESTAMPTZ NOT NULL
```

Constraints:

```text
FK turn_id → discord_session_turns.id ON DELETE CASCADE
CHECK chunk_index >= 0
UNIQUE (turn_id, chunk_index)
UNIQUE (discord_message_id)
```

The table design was selected instead of a turn column because it preserves
every chunk in exact delivery order. The global Discord-message uniqueness
prevents one returned message from being linked to multiple turns, while
per-turn chunk uniqueness prevents two messages from occupying the same
delivery position.

Migration properties:

- `down_revision = 20260726_14`;
- creates only the delivery table;
- performs no backfill;
- does not update or delete legacy rows;
- downgrade drops only `discord_turn_deliveries`;
- all pre-Sprint-2A.3 turns remain valid with zero delivery rows.

### Delivery Lifecycle

The code/test lifecycle is now:

```text
claim and model execution
→ response_text persisted
→ bot sends each Discord chunk exactly once in this execution
→ retain every returned discord.Message
→ collect message.id values in chunk order
→ completion POST sends execution_token + ordered message IDs
→ backend locks the turn
→ inserts all delivery rows
→ marks turn completed
→ commits delivery correlation and terminal state atomically
```

The bot does not acknowledge completion before every Discord send succeeds.
If a Discord send raises, completion is not called and no response ID is
persisted.

`send_discord_answer()` now returns all Discord message objects rather than
discarding them. Mention and slash-command paths both acknowledge the exact
returned IDs.

### Completion Idempotency and Conflict Policy

Completion request:

```json
{
  "execution_token": "<backend-owned-token>",
  "discord_response_message_ids": [
    "<chunk-0-message-id>",
    "<chunk-1-message-id>"
  ]
}
```

Rules:

- 1–16 unique, non-empty IDs are required;
- running-turn completion inserts IDs and completes in one transaction;
- retry after completion with the identical ordered list returns
  `completed` idempotently;
- retry with a different ID or different order returns HTTP 409 with
  `DISCORD_TURN_DELIVERY_CONFLICT`;
- an ID already linked to another turn also returns conflict;
- a completed legacy turn with no delivery rows is not retroactively
  overwritten by a new completion request.

The bot retries only a timeout/unavailable completion acknowledgement, up to
three attempts, always with the identical ID list. It does not re-run Discord
send while retrying the acknowledgement. This covers the required case where
Discord accepted the message but the completion response was temporarily
lost.

There remains an unavoidable external crash window if the bot process or host
dies after Discord accepts a message but before any completion request reaches
the backend. Persisting a Discord-returned ID cannot occur before Discord
returns it. Closing that machine-failure window completely would require a
future Discord idempotency nonce/durable delivery outbox design. Sprint 2A.3
does not hide this limitation; controlled completion retry and database
idempotency do prevent duplicate sends during ordinary ACK retry.

the backend performs an exact join:

```text

```

The lookup is constrained by:

```text
same session_id
originating sequence < current sequence
exact Discord response message ID
```

It does not search by content, display name, nearest message, or model-history
position.

### Resolution Status and Isolation Policy

The context contract now distinguishes:

```text
resolved_user_message
resolved_bot_response
not_found
outside_session
legacy_unavailable
```

Resolution order:

1. exact same-session user-source message;
2. exact same-session delivered bot-response message;
3. outside-session existence check without exposing content;
4. safe unresolved result.

If an exact ID belongs to another session, the context reports
`outside_session` and exposes neither originating request, assistant response,
nor author metadata. Similar text in two sessions cannot cause
cross-resolution.

Historical bot responses cannot be correlated because their Discord response
IDs were never captured. A Reply to such an unknown historical ID safely
resolves as `not_found`; no content-based backfill or guessing is attempted.
`legacy_unavailable` continues to represent a persisted legacy user target
whose trustworthy author metadata is unavailable.

Targets outside the ordinary six-turn history window still resolve by exact
delivery-table lookup.
